# AI 사용설명서 사이트 — 설계 문서

- 작성일: 2026-11-24
- 상태: 승인됨 (2026-11-24)
- 프로젝트 폴더(가칭): `~/ai-manual`

## 1. 의도와 이유

AI 모델·에이전트·스킬·활용법이 계속 쏟아지지만, 직장인과 비전공자는 찾아볼 시간이 없고 찾아도 설명이 어렵다. 이 사이트는 그 사람들 대신 찾아서, 가전제품 사용설명서처럼 쉽게 풀어준다.

만드는 이유 (사용자가 말한 것):
- 본인도 쓰려고 한다.
- 포트폴리오로 쓴다.
- 누구나 회원가입 없이 쓰는 공개 사이트로 연다.
- 수익 목적은 지금 없다. 나중에 생길 수도 있다.

## 2. 목표 / 하지 않는 것 / 실패 조건

**목표**
- 국내외 AI 소식을 매일 자동 수집해 쉬운 한국어 요약 + 원문 링크로 보여준다.
- 비전공자가 그대로 따라 하면 되는 단계별 가이드를 제공한다. 가이드는 사람이 직접 따라 해보고 승인한 것만 공개한다.
- 모든 글을 직군별(개발자, 디자이너, 기획자 등)로 골라 볼 수 있다.
- 회원가입 없이 전부 볼 수 있다.
- 운영비는 월 몇 달러 이내, 운영자가 손대지 않아도 뉴스는 계속 올라온다.

**하지 않는 것 (1차 버전)**
- 로그인, 회원, 댓글, 좋아요, 조회수
- DB, 관리자 화면
- 뉴스레터, 알림
- 다국어 (한국어만)
- 광고, 결제

**실패 조건 (동작해도 실패로 보는 것)**
- 검증 안 된 가이드가 공개된다.
- 기사 원문을 그대로 옮겨 싣는다.
- 요약이나 가이드에 전문용어가 풀이 없이 나온다.
- 운영자가 매일 손을 대야 사이트가 유지된다.

## 3. 제약

- 저작권: 원문 전문·이미지를 저장하거나 게시하지 않는다. 직접 쓴 3~5줄 요약 + 출처명 + 원문 링크만 싣는다.
- 수집은 공개 RSS만 쓴다 (작성자 판단: 검색 API는 1차 버전에서 뺀다. 유료이고 출처 통제가 어렵다. RSS로 부족하면 그때 추가).
- 요약을 위해 기사 본문을 잠깐 내려받는 것은 허용한다 (작성자 판단). 저장하지 않고, robots.txt가 막은 사이트와 로그인 필요한 페이지는 받지 않는다. 본문을 못 받고 RSS 발췌가 요약하기에 너무 짧으면 그 글은 건너뛴다. 모델이 내용을 지어내게 두지 않는다.
- 저장소는 공개로 둔다 (사용자 결정, 5.6 참고).
- API 키는 GitHub Actions 시크릿에만 둔다. 저장소와 사이트에 노출하지 않는다.

## 4. 검토한 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| **1. 정적 사이트 + 매일 자동 스크립트 (선택)** | 서버·DB 없음, 운영비 거의 0원, 검수는 PR 머지로 해결 | 조회수·댓글 같은 동적 기능 없음 |
| 2. Next.js + DB + 관리자 페이지 | 승인 화면, 통계, 회원 기능 확장 쉬움 | 만들 것 2~3배, DB·인증 운영 부담 |
| 3. 노션 + 사이트 빌더 | 가장 빠름 | 자동 수집 연결 어렵고 포트폴리오로 약함 |

1번을 고른 이유: 로그인 없는 읽기 전용 사이트라 동적 기능이 필요 없고, 운영비와 손이 가장 적게 든다. 글이 마크다운 파일이라 나중에 2번으로 옮기기 쉽다.

## 5. 구조

```
[매일 1회 GitHub Actions]
  수집(RSS) → URL 중복 제거 → 같은 사건 묶기·선별 → 본문 받기 → Claude API 요약·직군 분류 → 베낌 검사
    → 뉴스: 마크다운 파일로 main에 자동 커밋 → 자동 배포
    → 가이드 후보: 주 1회 초안을 PR로 생성 → 운영자가 따라 해보고 머지 → 배포
```

### 5.1 사이트 (작성자 판단: Astro)

- Astro 정적 빌드, 콘텐츠 컬렉션 두 개: `news`, `guides`
- 호스팅: Cloudflare Pages 무료 플랜 (작성자 판단). Vercel 무료 플랜은 상업적 이용을 금지해 나중에 광고·수익화 때 옮겨야 하고, 비공개 저장소의 봇 커밋 배포도 막는다. 무료 한도 수치는 구현 직전에 공식 문서로 다시 확인한다.
- 검색: Pagefind (빌드 때 만들어지는 정적 검색, 서버 불필요)

페이지:
- `/` — 최신 뉴스 요약 + 최신 가이드
- `/news` — 뉴스 목록, 직군 필터
- `/guides` — 가이드 목록, 직군·난이도 필터
- `/guides/[slug]` — 가이드 본문
- `/role/[role]` — 직군별 모아보기
- `/about` — 사이트 소개, 요약·검수 방식, 저작권 문의 연락처

뉴스는 개별 상세 페이지 없이 목록 카드에서 요약을 보여주고 원문으로 내보낸다.

방문 통계와 제보 (사용자 결정):
- Cloudflare Web Analytics를 붙여 운영자가 어떤 글이 읽히는지 본다. 사이트 화면에 조회수는 표시하지 않는다.
- 가이드마다 "여기서 막혔어요" 링크를 둔다. 가이드 제목이 미리 채워진 구글 폼(또는 메일)으로 연결한다.
- 댓글, 좋아요, 화면 표시 조회수, 인기글 순위는 넣지 않는다 (사용자와 합의, 방문자가 생긴 뒤 재검토).

### 5.2 직군 분류 (작성자 판단, 고정 5개)

`개발자`, `디자이너`, `기획·PM`, `마케터`, `일반 사무`

한 글에 여러 직군을 붙일 수 있다. 목록은 설정 파일 한 곳에서 관리한다.

### 5.3 콘텐츠 형식

뉴스 (`src/content/news/YYYY-MM-DD-slug.md`):
- `title` 쉬운 한국어 제목
- `date`, `sourceName`, `sourceUrl`, `lang`(ko/en)
- `roles[]`
- `summary` 3~5줄
- `whyItMatters` "그래서 나한테 뭐가 달라지나" 한 줄

가이드 (`src/content/guides/slug.md`):
- `title`, `roles[]`, `difficulty`(쉬움/보통/어려움), `minutes`(소요 시간)
- `tools[]` 필요한 것
- `verifiedAt` 운영자가 직접 따라 해본 날짜 — 화면이 바뀌면 낡은 가이드임을 독자가 알 수 있게 본문 상단에 표시
- 본문 고정 틀: 이걸 하면 뭐가 좋은가 → 준비물 → 단계별 따라하기 → 막혔을 때 → 원문·참고 링크

### 5.4 수집 파이프라인

- 출처 목록은 `sources.json` 한 파일. 처음엔 주요 AI 회사 공식 블로그와 국내외 AI 매체 RSS 10~15개로 시작.
- 중복 제거: 이미 저장된 글의 `sourceUrl`과 비교.
- 같은 사건 묶기·선별 (작성자 판단): 그날 후보의 제목·발췌를 한 번에 모델에 주고, 같은 사건은 하나로 묶어 대표 글 하나만 남긴다. 대표는 공식 블로그 우선, 그다음 한국어 매체. AI와 무관하거나 일반인에게 쓸모없는 글은 여기서 `skip`. 남은 것 중 일반인에게 쓸모 있는 순으로 최대 10건.
- 하루 게시 상한 10건 (비용·품질 상한).
- 베낌 검사 (작성자 판단): 요약에 원문과 연속으로 길게 겹치는 구간이 있으면 게시하지 않는다. 단순 문자열 비교이고 두 번째 모델 검토는 두지 않는다. 쉬운 말 쓰기는 프롬프트로 지시한다.
- 잘못된 요약이 나갔을 때는 해당 파일을 지우는 커밋으로 처리한다. 별도 도구는 없다.
- 요약은 저렴한 모델, 가이드 초안은 상위 모델을 쓴다.
- 한 글이 실패하면 그 글만 건너뛴다. 전체가 실패하면 사이트는 그대로 유지되고 GitHub가 실패 메일을 보낸다.

### 5.5 가이드 검수 흐름

- 주 1회 작업이 그 주 뉴스 중 "따라 할 수 있는 것"을 1~2개 골라 가이드 초안을 PR로 올린다.
- 초안의 재료 (작성자 판단): 주간 작업이 원문과 공식 문서를 Claude API의 웹 검색·가져오기 도구로 다시 읽고 쓴다. 저장된 3~5줄 요약만으로 쓰지 않는다. 확인하지 못한 메뉴 이름·버튼 위치는 추측해 적지 말고 `[확인 필요]`로 표시한다.
- 운영자가 직접 따라 해보고, 틀린 단계를 고치고, `verifiedAt`을 채워 머지한다.
- 스크린샷은 선택 (작성자 판단). 운영자가 검수하면서 직접 찍은 것만 `src/assets/guides/<slug>/`에 둔다. 초안은 글만 있다.
- `verifiedAt`이 없는 가이드는 실제 사이트 빌드에서 제외한다 (작성자 판단: 빌드 실패 대신 제외). PR 미리보기에서는 "미검증 초안" 띠를 달고 보여서 운영자가 렌더링된 모습을 확인할 수 있다. 미리보기 주소는 검색엔진 수집을 막는다.
- 운영자가 직접 쓴 가이드도 같은 틀로 추가할 수 있다.

### 5.6 저장소 공개 여부

- 공개 저장소를 전제로 한다. 포트폴리오 목적에 맞고 GitHub Actions가 무료다.
- 공개 저장소에서는 미검증 초안 PR이 GitHub에서 누구에게나 보인다. 사이트에는 나오지 않으므로 "검증 안 된 가이드 공개"로 보지 않는다. PR 제목에 `[초안·미검증]`을 붙인다.
- 비공개로 바꿔도 호스팅은 그대로 쓸 수 있다. 다만 GitHub Actions 무료 실행 시간에 한도가 생긴다.

### 5.7 보안

- API 키는 GitHub Actions 시크릿에만 둔다. GitHub의 시크릿 스캔과 푸시 보호를 켠다.
- Anthropic 콘솔에서 월 사용 한도를 걸어, 키가 새거나 파이프라인이 폭주해도 요금이 한도에서 멈추게 한다.
- 워크플로는 `pull_request_target`을 쓰지 않는다. 외부 사람의 PR에서는 시크릿이 있는 작업이 돌지 않게 하고, 외부 기여자의 워크플로 실행은 승인제로 둔다.
- 워크플로 토큰 권한은 필요한 최소(콘텐츠 쓰기, PR 생성)만 준다. 외부 액션은 커밋 해시로 고정한다.
- 수집한 기사 내용은 신뢰하지 않는 입력이다. 매일 요약 단계의 모델에는 도구를 주지 않고, 출력은 정해진 필드(구조화 출력)로만 받는다. 요약 본문에 HTML·스크립트·임의 링크를 허용하지 않고, 링크는 `sourceUrl` 하나만 싣는다.
- 웹 도구를 쓰는 주간 가이드 작업의 결과는 PR로만 나가고 사람이 읽은 뒤 머지한다.

## 6. 확인 방법

- 콘텐츠 스키마 검증은 Astro 빌드가 한다 (형식이 틀리면 빌드 실패).
- 파이프라인은 URL 중복 제거와 베낌 검사에 대한 작은 테스트 하나. 사건 묶기·선별은 모델 판단이라 자동 테스트 대신 첫 주 결과를 눈으로 확인한다.
- 배포 전 수동 확인: 뉴스 자동 게시 1회, 가이드 PR 생성→머지→공개 1회.

## 7. 만드는 사람에게 맡기는 것

- 시각 디자인 (비전공자가 편하게 읽는 큰 글씨·넓은 여백 방향, 모바일 우선)
- 초기 출처 목록의 구체적 항목
- 요약·가이드 프롬프트 문구
- 저장소 이름, 도메인

## 8. 나중에 필요해지면

- 조회수·인기글, 뉴스레터, 댓글, 회원, 수익화 → 그때 DB를 붙이거나 2번 방식으로 이전
